Sobre Yalla

Yalla agrupa la data de diferentes sistemas, centraliza los procesos específicos de nuestra operación, automatiza todos los pasos que son calculables e involucra agentes de IA en los procesos que requieren razonamiento.

La data sigue existiendo en sus puntos originales de creación. Yalla la interpreta, la automatiza y la reescribe cuando hace falta para mantener la coherencia entre todos los sistemas.

Qué se comparte. Datos operativos de inmuebles, reservas, huéspedes, visitas, limpieza, mantenimiento, casos, inventario, compras y usuarios de operación.
Qué no se comparte. Finanzas, porque esa sección sigue en desarrollo. Credenciales, permisos internos, avisos de Slack y ejecuciones de agentes.

About Yalla

Yalla groups data from different systems, centralizes the specific processes of our operation, automates every step that can be calculated, and brings in AI agents for processes that require reasoning.

The data still lives at its original points of creation. Yalla interprets it, automates it, and writes it back when that is needed to keep the data coherent across all systems.

What is shared. Operational data for properties, bookings, guests, visits, cleaning, maintenance, cases, inventory, purchases, and operations users.
What is not shared. Finance, because that section is still in development. Credentials, internal permissions, Slack notices, and agent runs.

Origen Guesty

Guesty es el origen de inmuebles, reservas, reseñas y de una parte de las tareas. Yalla copia esos registros a sus tablas y les añade campos propios: planificación, check-in, limpieza, mantenimiento, casos e inventario. El identificador de conversación se guarda; el texto del inbox no.

La API de lectura sirve la copia que Yalla ya tiene. Guesty no es una segunda puerta de este catálogo.

Guesty origin

Guesty is the origin of properties, bookings, reviews, and part of the tasks. Yalla copies those records into its tables and adds its own fields: planning, check-in, cleaning, maintenance, cases, and inventory. The conversation id is stored; inbox text is not.

The read API serves the copy Yalla already holds. Guesty is not a second door in this catalog.

API de lectura

Todos los dominios accesibles usan la misma llamada. Cambia solo el nombre del recurso. Base: https://1imz55h7b2.execute-api.eu-central-1.amazonaws.com/prod/v1

Solo GET. Cabecera obligatoria: x-api-key. La clave se entrega aparte y no está en este documento. Tope: 5 peticiones por segundo, ráfaga 10, 10.000 al día. Sin clave la respuesta es 403. Un nombre que no esté en la lista responde 404.

No hay filtro por inmueble, fecha ni identificador. Cada llamada devuelve una página de toda la tabla. Por defecto 50 filas, máximo 100. Si nextCursor no es null, la página siguiente repite la misma ruta con cursor igual a ese valor.

Ejemplo: reservas

curl -s \
  -H "x-api-key: TU_CLAVE" \
  "https://1imz55h7b2.execute-api.eu-central-1.amazonaws.com/prod/v1/bookings?limit=50"
{
  "resource": "bookings",
  "items": [
    {
      "ReservationID": "ejemplo",
      "ListingID": "ejemplo",
      "GuestName": "Huésped de ejemplo",
      "Status": "confirmed",
      "CheckInDate": "2026-10-06"
    }
  ],
  "nextCursor": "token-opaco"
}

La página siguiente:

GET /v1/bookings?limit=50&cursor=token-opaco

El check-in va dentro de bookings. Finanzas no tiene ruta. El resto de dominios accesibles se pide igual, cambiando el último segmento:

  • Inmuebles: /v1/properties
  • Reservas: /v1/bookings
  • Reseñas: /v1/reviews
  • Visitas y planificación: /v1/visits, /tasks, /visit-types, /teams, /visit-templates, /planner-settings, /users, /job-scheduler
  • Limpieza: /v1/cleaning-plans, /cleaning-incidents, /property-cleaning-details, /cleaners
  • Mantenimiento: /v1/maintenance-plans, /maintenance-incidents, /maintenance-providers, /maintenance-agents
  • Casos: /v1/cases, /case-events
  • Inventario y compras: /v1/inventory, /purchases, /subtractions

GET /v1 devuelve esa misma lista de nombres y los límites de página.

Read API

Every accessible domain uses the same call. Only the resource name changes. Base: https://1imz55h7b2.execute-api.eu-central-1.amazonaws.com/prod/v1

GET only. Required header: x-api-key. The key is delivered separately and is not in this document. Limits: 5 requests per second, burst 10, 10,000 per day. Without a key the response is 403. A name that is not in the list returns 404.

There is no filter by property, date, or id. Each call returns one page of the whole table. Default 50 rows, maximum 100. When nextCursor is not null, the next page repeats the same path with cursor set to that value.

Example: bookings

curl -s \
  -H "x-api-key: YOUR_KEY" \
  "https://1imz55h7b2.execute-api.eu-central-1.amazonaws.com/prod/v1/bookings?limit=50"
{
  "resource": "bookings",
  "items": [
    {
      "ReservationID": "example",
      "ListingID": "example",
      "GuestName": "Example guest",
      "Status": "confirmed",
      "CheckInDate": "2026-10-06"
    }
  ],
  "nextCursor": "opaque-token"
}

The next page:

GET /v1/bookings?limit=50&cursor=opaque-token

Check-in is inside bookings. Finance has no path. The other accessible domains use the same call, with a different last segment:

  • Properties: /v1/properties
  • Bookings: /v1/bookings
  • Reviews: /v1/reviews
  • Visits and planning: /v1/visits, /tasks, /visit-types, /teams, /visit-templates, /planner-settings, /users, /job-scheduler
  • Cleaning: /v1/cleaning-plans, /cleaning-incidents, /property-cleaning-details, /cleaners
  • Maintenance: /v1/maintenance-plans, /maintenance-incidents, /maintenance-providers, /maintenance-agents
  • Cases: /v1/cases, /case-events
  • Inventory and purchases: /v1/inventory, /purchases, /subtractions

GET /v1 returns that same list of names and the page limits.

Arquitectura

La aplicación es Amplify Gen2 en eu-central-1. El personal entra con Cognito. Casi todas las lecturas y escrituras del día son Lambdas con URL pública y un JWT comprobado en el código. DynamoDB es el almacén. Guesty, las cerraduras y Slack entran por Lambdas externas al pipeline de Amplify. OpenAI se usa en Agent Studio. La API de este catálogo es otro API Gateway, solo lectura, con clave propia, y no usa el usuario de Cognito del personal.

Architecture

The app is Amplify Gen2 in eu-central-1. Staff sign in with Cognito. Most day-to-day reads and writes are Lambdas with a public URL and a JWT checked in code. DynamoDB is the store. Guesty, the door systems, and Slack arrive through Lambdas outside the Amplify pipeline. OpenAI is used in Agent Studio. The API in this catalog is a separate API Gateway, read-only, with its own key, and it does not use a staff Cognito user.

Agent Studio

Aquí se agrupan los agentes que Yalla utilizará y la lista de tools con las que automatizan los procesos que requieren razonamiento. Está en una fase de desarrollo preliminar, hasta que los datos generados de la operación y de las finanzas tengan la consistencia que se busca. Estas ejecuciones no salen por la API de lectura.

Agent Runtime

Cada ejecución toma una versión del agente. Una prueba usa el borrador. La producción usa la versión publicada. El runtime envía al modelo las instrucciones, las reglas y solo las tools permitidas para ese agente. El modelo responde o pide una tool. El runtime la ejecuta, guarda el paso y devuelve el resultado al modelo. El ciclo sigue hasta una respuesta final o hasta un límite: 8 turnos, 90 segundos, 0,50 USD y 12 llamadas a tools. Si una tool escribe hacia fuera, como un mensaje al inbox, la ejecución se detiene y espera aprobación.

Agentes, versiones y memoria

Cada agente conserva un borrador y las versiones publicadas. Publicar fija una versión. Esa versión incluye instrucciones, reglas, tools permitidas, modelo y política de memoria. La memoria puede ser ninguna, o equivalencias aprendidas. La revisión de facturas de limpieza guarda, entre ejecuciones, qué concepto de la factura corresponde a qué tipo de limpieza en Yalla, y las conciliaciones siguientes reutilizan ese mapa. Cada ejecución queda registrada con sus pasos.

Hoy hay tres agentes publicados: el relato de llegadas en Madrid, el briefing de llegadas de hoy y la revisión de facturas de limpieza.

Tools

La lista es común. Cada agente solo puede llamar a las que tiene permitidas. Hoy: huéspedes con check-in hoy, avisos de reservas próximas, lectura del hilo de una reserva, envío de un mensaje a ese hilo con aprobación, verificación de una factura de limpieza y conciliación de esa factura. La conciliación es la que persiste la memoria de equivalencias.

Agent Studio

This is where Yalla groups the agents it will use, and the tool list those agents use to automate processes that require reasoning. It is in a preliminary development phase, until the data generated from operations and from finance has the consistency being sought. These runs are not on the read API.

Agent Runtime

Each run takes one version of an agent. A test uses the draft. Production uses the published version. The runtime sends the model the instructions, the rules, and only the tools allowed for that agent. The model answers or asks for a tool. The runtime runs it, stores the step, and returns the result to the model. The loop continues until a final answer or a limit: 8 turns, 90 seconds, 0.50 USD, and 12 tool calls. If a tool writes outward, such as an inbox message, the run stops and waits for approval.

Agents, versions, and memory

Each agent keeps a draft and its published versions. Publishing freezes a version. That version includes instructions, rules, allowed tools, model, and memory policy. Memory can be none, or learned equivalences. Cleaning invoice review stores, across runs, which invoice concept matches which Yalla cleaning type, and later reconciliations reuse that map. Every run is stored with its steps.

Three agents are published today: the Madrid arrivals story, today's arrivals brief, and cleaning invoice review.

Tools

The list is shared. Each agent can call only the tools it is allowed to use. Today: guests checking in today, upcoming reservation warnings, reading a reservation thread, sending a message on that thread with approval, verifying a cleaning invoice, and reconciling that invoice. Reconciliation is what persists the equivalence memory.

Lecturas del personal

Las funciones get-properties, get-bookings, get-visits y el resto de lecturas de la aplicación son del personal. Exigen un usuario de Cognito. Un proveedor no las llama y no recibe un usuario de ese grupo.

La lectura compartida es solo la API de este documento: GET /v1/{recurso} con clave. Esas dos puertas no son intercambiables.

Staff reads

The functions get-properties, get-bookings, get-visits, and the rest of the app reads belong to staff. They require a Cognito user. A provider does not call them and does not receive a user in that group.

Shared reading is only the API in this document: GET /v1/{resource} with a key. The two doors are not interchangeable.
